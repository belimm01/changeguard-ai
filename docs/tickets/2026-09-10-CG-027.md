# CG-027 — Add structured logging, metrics, and health/readiness probes

Date: 2026-09-10
Status: Planned
Dependencies: CG-025, CG-026

## Outcome

ChangeGuard exposes privacy-preserving structured logs, operational metrics, liveness, and readiness endpoints that let operators understand ingestion, worker, database, GitHub publishing, and optional AI-provider health without leaking source content or secrets.

## Design principles

- Liveness asks whether the process should be restarted; readiness asks whether it can serve useful traffic now.
- Structured logs are machine-readable events with explicit fields, not formatted payload dumps.
- Metrics should describe rates, latency, counts, and failure categories without cardinality explosions.
- Privacy is an observability requirement: source code, patches, tokens, prompts, and model outputs are sensitive.

## Contract

1. Emit structured logs for webhook receipt, authorization decisions, job claim/heartbeat/complete/fail, analysis completion, outbox publish attempts, GitHub API error categories, and readiness dependency failures.
2. Every log event must include bounded identifiers such as delivery id, job id, repository id, installation id, pull request number, head SHA prefix, status, duration, and error category where relevant.
3. Logs must not include raw request bodies, diffs, full file content, tokens, private keys, webhook secrets, prompts, model responses containing source, or full exception dumps with sensitive values.
4. Expose metrics for request counts/latency, webhook accept/reject counts by reason, job state counts, job duration, worker lease recovery counts, outbox publish attempts/failures, GitHub API latency/error categories, and optional AI usage when enabled.
5. Avoid high-cardinality labels such as full repository name, file path, raw error message, delivery id, job id, or SHA as metric labels.
6. `/live` should succeed when the process event loop/server is alive, even if dependencies are down.
7. `/ready` should fail when required dependencies for the configured role are unavailable, such as database connectivity for API/worker, migration mismatch, or required GitHub App configuration in GitHub mode.
8. Optional AI provider readiness is required only when opt-in AI mode is enabled.
9. Health endpoints must not require external writes and must have bounded timeouts.

## TDD loop

Start with a failing redaction test:

```bash
uv run pytest tests/unit/test_observability_redaction.py::test_structured_log_redacts_tokens_and_raw_content -q
```

Expected first failure: observability module or redaction helper does not exist.

Then add tests:

- webhook rejection logs reason without raw payload;
- worker completion logs job identifiers and duration;
- metrics endpoint contains expected counters without high-cardinality labels;
- `/live` succeeds when database is unavailable;
- `/ready` fails when database is unavailable for the API role;
- `/ready` fails on migration mismatch if migration state is tracked;
- optional AI provider readiness is skipped when AI mode is disabled.

## Acceptance criteria

- Unit tests prove redaction for secrets and raw content in representative log events.
- Integration tests prove `/live` and `/ready` differ when dependencies fail.
- Metrics expose useful operational signals without unbounded labels.
- Worker, webhook, and outbox paths emit structured events with shared correlation identifiers.
- Readiness behavior is role-aware and bounded by timeouts.
- Documentation or README updates explain the observability contract and privacy limits.

## Error, security, and privacy cases

- Do not log `Authorization`, `X-Hub-Signature-256`, private key PEM, installation token, webhook body, patch, source file content, prompt, or model response text.
- Normalize unexpected exceptions into error categories for metrics; retain detailed traceback only in safe local debug mode if explicitly configured.
- Health endpoints should not reveal secrets or internal stack traces.
- Metrics should not let a caller infer private file paths or code contents.

- Operators can distinguish live process, ready service, dependency outage, webhook failures, worker backlog, and Check publishing failures.
- Privacy-sensitive data is absent from logs and metrics by tested construction.
- Observability is useful in local Compose and future single-host deployment without requiring Kubernetes.
