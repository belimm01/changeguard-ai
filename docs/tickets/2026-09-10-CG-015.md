# CG-015 — Persist analysis jobs and reports with async SQLAlchemy, Postgres, and Alembic

Date: 2026-09-10
Status: Planned
Depends on: CG-014

## Outcome

ChangeGuard stores analysis jobs and versioned reports in PostgreSQL using async SQLAlchemy models and Alembic migrations, with uniqueness by repository, PR, head/base SHA, and analysis version plus explicit queued/running/completed/partial/failed states.

## Design principles

- Persistence records observed analysis state; it must not change the advisory product contract.
- Async database sessions need transaction boundaries and deterministic tests.
- A uniqueness constraint prevents duplicate work for the same PR revision and analysis version; idempotent webhooks build on this in CG-024.

## Files

Create proposed:

- `src/changeguard/db/base.py` — SQLAlchemy metadata/model base.
- `src/changeguard/db/models.py` — analysis job and report persistence models.
- `src/changeguard/db/session.py` — async engine/session factory helpers.
- `src/changeguard/repositories/analysis_jobs.py` — small repository layer for job/report operations.
- `alembic.ini` — Alembic configuration if the project has none.
- `alembic/env.py` — migration environment using project metadata.
- `alembic/versions/<revision>_create_analysis_jobs.py` — initial schema migration.
- `tests/integration/db/test_analysis_jobs_repository.py` — repository behavior tests.
- `tests/integration/db/test_migrations.py` — migration smoke test if a disposable database is available.

Modify existing:

- `pyproject.toml` and `uv.lock` — add `sqlalchemy`, `asyncpg`, and `alembic` with bounded major ranges.
- `src/changeguard/config.py` — add database URL settings without logging credentials.
- `src/changeguard/api/app.py` — only if the endpoint should write/read jobs after the repository exists.

## Data model requirements

Persist at least:

- Repository owner/name and PR number.
- Base SHA, head SHA, and analysis version.
- Job state: `queued`, `running`, `completed`, `partial`, `failed`.
- Request timestamps and completion timestamps.
- Serialized versioned report JSON for completed/partial/failed-with-report states.
- Failure reason sanitized for logs/UI.
- Lease owner and lease expiration fields may be nullable placeholders for CG-025 recovery.

## Acceptance criteria

- Alembic creates the tables and constraints from an empty real PostgreSQL database; a mock-only migration check is not sufficient acceptance evidence.
- A uniqueness constraint prevents duplicate jobs for the same repository, PR, base SHA, head SHA, and analysis version.
- Creating a duplicate returns the existing job or raises a typed duplicate result as intentionally designed; it must not create two rows.
- Valid state transitions are enforced in code: queued → running → completed/partial/failed. Invalid transitions are tested.
- Stored report JSON preserves the CG-008 schema version and exact base/head SHAs.
- Failed jobs store a sanitized reason without raw tokens, patches, or repository content.
- Async SQLAlchemy sessions are committed/rolled back explicitly; repository integration tests exercise PostgreSQL transaction behavior rather than replacing it with in-memory fakes.
- Database credentials come from configuration and are not printed.
- Worker lease recovery is represented as future-compatible nullable fields only; actual recovery is CG-025.

## Non-goals

- No durable worker loop, webhook idempotency queue, Check Run publishing, observability stack, or deployment manifest.
- No ORM model for every future report subobject unless needed for the current queries.
- No SQLite production target; acceptance requires a disposable PostgreSQL service for migration and repository integration tests. If unavailable, record CG-015 as blocked/partial rather than claiming persistence is implemented.
