# CG-011 — Add a scoped OpenAPI breaking-change rule

Date: 2026-09-10
Status: Done
Depends on: CG-010

## Outcome

ChangeGuard detects a small, documented subset of OpenAPI breaking changes between base and head content, emits line/path evidence where available, and reports unsupported OpenAPI features as coverage rather than pretending complete analysis.

## Design principles

- Deterministic compatibility rules should start with a narrow subset and precise coverage.
- YAML/JSON documents are untrusted input; parse safely and reject resource-heavy shapes.
- A breaking-change rule compares base and head semantic structures, not raw text alone.

## Files

Create proposed:

- `src/changeguard/rules/openapi.py` — scoped OpenAPI compatibility rule.
- `src/changeguard/parsing/openapi.py` — safe parsing helpers if separation keeps the rule simple.
- `tests/unit/rules/test_openapi.py` — rule tests for supported changes and unsupported coverage.
- `tests/fixtures/openapi/` — small base/head specs used by tests.

Modify existing:

- `src/changeguard/application/analysis.py` or rule registry/composition point — include this rule only after content inputs exist.
- `src/changeguard/domain/content.py` and `src/changeguard/domain/reports.py` — use existing content/evidence/coverage types.
- `pyproject.toml` and `uv.lock` — add a safe YAML parser only if JSON-only parsing is insufficient; prefer `PyYAML` with bounded major range if needed.

## Supported v1 subset

Detect at least these scenarios for OpenAPI 3.x documents:

- Removing a path.
- Removing an HTTP operation from an existing path.
- Removing a response status code from an existing operation.
- Adding a required request parameter to an existing operation.
- Adding a required property to an existing object schema used by request bodies, if schema traversal is implemented in a small bounded way.

Everything outside the implemented subset must be represented in coverage as unsupported or not evaluated.

## Acceptance criteria

- Safe parsing handles JSON and, if dependency is added, YAML without object construction or arbitrary tags.
- Invalid or oversized specs produce partial coverage, not rule crashes or safe results.
- Removing `GET /users` or removing `/users` emits a deterministic high- or medium-risk finding with evidence path and line/source references when available.
- Adding a required query parameter to an existing operation is detected.
- OpenAPI 2.0, callbacks/webhooks/links, complex `$ref` graphs, remote refs, composed schemas, or any unimplemented feature are reported as unsupported coverage.
- The rule does not fetch remote refs, execute generators, or import code from the repository.
- Findings are advisory and serialized through the report model from CG-008.

## Non-goals

- No complete OpenAPI diff engine.
- No remote `$ref` resolution.
- No LLM explanation, UI, or policy enforcement.

## Ordered TDD steps

1. Create tiny base/head fixture specs for one removed operation.
2. Write the failing rule test and expected finding summary/evidence.
3. Implement safe parse and the minimal path/operation comparison.
4. Add failing tests for removed response and added required parameter.
5. Implement each comparison with deterministic ordering.
6. Add failing invalid YAML/JSON, oversized, and unsupported-feature coverage tests.
7. Implement conservative coverage states.
8. Wire the rule into the analysis composition point if that point exists after CG-010, then run gates.
