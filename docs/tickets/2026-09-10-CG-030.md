# CG-030 — Verify v1 end-to-end release acceptance and handoff

Date: 2026-09-10
Status: Planned
Dependencies: CG-011, CG-012, CG-013, CG-021, CG-022, CG-026, CG-027, CG-028, CG-029

## Outcome

ChangeGuard v1 is accepted only after an approved sandbox end-to-end demonstration proves PR analysis, advisory Check publishing, worker recovery, deployment rollback, persistence, backup/restore, offline evaluation, leakage protections, and documented product limits without fabricating green evidence or performing unapproved production release actions.

## Design principles

- Release acceptance is evidence collection against explicit scope, not a final burst of feature work.
- A demo using a sandbox repository is still a real external write and needs explicit approval.
- Operational readiness includes restart recovery, rollback, persistence, and backup restore.
- Non-goals protect trust: optional extensions are not required for v1 and should not masquerade as complete.

## Contract

1. Define the v1 acceptance checklist before running the demo. Every item must have an evidence source: automated test output, local command output, sandbox URL, screenshot reference, log excerpt, or explicit non-goal.
2. Obtain explicit user approval before any live external write: creating/updating GitHub Checks, installing a GitHub App, pushing branches, deploying services, or calling paid AI providers.
3. Use an approved sandbox repository and pull request for the real PR flow. Do not run against an untrusted production repository.
4. Demonstrate advisory analysis on the exact head SHA, including OpenAPI, Avro, and Kubernetes subset behavior where fixtures or sandbox changes cover them.
5. Observe a real GitHub Check result after readback. The Check must be advisory and must not claim merge safety.
6. Demonstrate worker restart recovery: enqueue or select a job, interrupt/restart the worker, and prove the job completes or retries safely.
7. Demonstrate persistence across service restart and database restart where feasible in the local Compose environment.
8. Demonstrate backup and restore on disposable data and verify restored records.
9. Demonstrate rollback using the CG-028 runbook, including image version rollback and database restore/compatibility notes.
10. Run offline evaluation and injection/leakage regression gates. If opt-in AI is approved, record provider, model, cost/usage, and deterministic fallback comparison.
11. Document measured limits: payload size, max files, timeout, retry limits, worker concurrency, API rate-limit behavior, and unsupported PR/repository scenarios.
12. Document completed v1 scope, non-goals, and optional extensions. Do not require optional extensions for v1 acceptance.
13. No public release, package publish, production deployment, or repository merge happens until separately authorized.

## TDD/evidence loop

Start by creating a failing or incomplete acceptance checklist item, not by running a demo:

```bash
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
uv run mypy src tests
uv lock --check
```

Then fill evidence as gates and approved demo steps pass. For a sandbox e2e harness, first add a skipped test with a clear marker requiring explicit credentials/approval, then enable it only in the approved environment.

Proposed approval-gated command shape:

```bash
CHANGEGUARD_SANDBOX_APPROVED=true uv run pytest tests/e2e/test_v1_sandbox_flow.py -q
```

The environment variable is not permission by itself; it records that separate human approval was obtained.

## Acceptance criteria

- Acceptance checklist covers every dependency named in this ticket and marks each item as passed, failed, blocked, or non-goal with evidence.
- A sandbox real PR flow is observed only after approval and includes readback of the GitHub Check result.
- Restart recovery, persistence, backup/restore, and rollback are demonstrated with real command output or clearly recorded blockers.
- Offline eval and injection/leakage regressions pass with real output; no fabricated green status is accepted.
- Runtime AI remains optional, but claiming the full AI-capable v1 requires an
  approved cost-bounded live run of the CG-018 concrete adapter through retrieval,
  citation validation and report enrichment, compared with deterministic-only
  behavior. If approval or credentials are unavailable, record AI acceptance as
  blocked and label the demonstrated release deterministic-only; do not claim
  the complete AI-capable project has been verified.
- Handoff docs state measured limits, completed scope, non-goals, operating commands, and known risks.
- No real production deployment, public release, package publication, merge, or external write occurs without explicit approval.

## Security, release, and recovery cases

- Treat sandbox repository content as untrusted input even though the repository is approved for testing.
- Redact secrets from evidence logs and screenshots before committing documentation.
- Record failed demo steps. A partial failure is a release blocker or known limitation, not something to paper over.
- Do not conflate a passing advisory Check with merge readiness.

## Definition of done

- v1 has a complete evidence-backed acceptance record and handoff document.
- Every live external action was approved beforehand and read back afterward.
- Operators can run, monitor, back up, restore, and roll back the system from the docs.
- The project states what v1 does, what it does not do, and what optional extensions remain future work.
