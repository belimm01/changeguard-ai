# CG-024 — Verify GitHub webhooks and durably enqueue analysis

Date: 2026-09-10
Status: Planned
Dependencies: CG-015, CG-023

## Outcome

A bounded FastAPI webhook endpoint verifies GitHub HMAC signatures over the raw request body, authorizes the repository installation, records each delivery idempotently, and transactionally enqueues one analysis job for accepted pull-request events.

## Design principles

- Webhook signatures must be checked against the exact raw bytes received, before JSON parsing changes representation.
- Idempotency belongs in durable storage, not in process memory.
- Accepted HTTP responses should mean durable work was recorded, not merely scheduled in a background task.
- Filtering event/action scope is a security boundary as well as a product choice.

## Contract

1. Accept only GitHub webhook requests with valid `X-Hub-Signature-256`, `X-GitHub-Event`, and `X-GitHub-Delivery` headers.
2. Read at most the configured maximum raw body bytes. Reject oversized payloads before attempting JSON parsing.
3. Verify `sha256=` HMAC using constant-time comparison against the raw bytes exactly as received.
4. Parse JSON only after signature verification succeeds.
5. Process only pull-request events/actions that can affect analysis, such as opened, reopened, synchronize, and ready_for_review. Explicitly ignore unrelated events/actions with a safe 2xx response and no job.
6. Verify the payload repository and installation against CG-023 authorization before writing an analysis job.
7. Insert the webhook delivery into a durable inbox keyed by delivery id and provider. Duplicate deliveries must not create repeated analysis jobs.
8. Insert/update the analysis job in the same database transaction as the accepted inbox record.
9. Do not use FastAPI in-process background tasks for accepted durable work. The worker introduced later must read persisted jobs.
10. Return bounded, non-secret diagnostics. Never log raw payloads, diffs, webhook secrets, or tokens.

## TDD loop

Start with a failing test:

```bash
uv run pytest tests/unit/test_github_webhook_signature.py::test_rejects_signature_computed_for_different_raw_bytes -q
```

Expected first failure: signature verifier does not exist.

Build outward in this order:

- valid signature over raw bytes is accepted;
- missing/malformed signature is rejected;
- same JSON with different whitespace fails if signature is for the other bytes;
- oversized body fails before JSON parse;
- unsupported event/action records no job;
- invalid repository/installation authorization records no job;
- duplicate delivery id returns idempotently and creates no second job;
- database failure rolls back both inbox and job rows.

## Acceptance criteria

- Invalid signatures, missing signatures, wrong algorithms, malformed headers, and oversized bodies are rejected before trusted parsing or enqueue.
- Duplicate `X-GitHub-Delivery` values are idempotent across process restarts because state is in the database.
- Accepted pull-request events create at most one queued analysis job for the repository/PR/head SHA/analysis version uniqueness boundary from CG-015.
- Inbox insertion and job enqueue are one transaction; tests prove rollback behavior.
- No accepted durable work depends on in-process `BackgroundTasks`.
- Logs and HTTP errors avoid raw content, patches, secrets, tokens, and full payload dumps.

## Security, concurrency, and recovery

- Treat all webhook payload fields as untrusted even after HMAC verification; the signature proves GitHub origin, not business authorization.
- Idempotency must survive retries, deployments, and worker crashes.
- Race duplicate deliveries in concurrent tests; assert one inbox record and one job.
- Preserve enough metadata for later audit: provider, delivery id, event, action, installation id, repository id/name, pull request number, head SHA, received time, and processing status.

## Definition of done

- Webhook acceptance is signature-verified, authorization-checked, idempotent, and durable.
- Replayed deliveries and concurrent duplicates do not create repeated jobs.
- Invalid input and unsupported actions are observable without exposing sensitive material.
- The worker can later consume persisted jobs without relying on the web process staying alive.
