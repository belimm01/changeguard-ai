# CG-025 — Process analysis jobs with durable worker leases

Date: 2026-09-10
Status: Planned
Dependencies: CG-015, CG-020, CG-024

## Outcome

A worker process durably claims queued analysis jobs with leases, heartbeats while running, retries recoverable failures, releases stale work after crashes, and shuts down gracefully without pretending to provide exactly-once execution.

## Design principles

- Job queues in a database are at-least-once systems unless proven otherwise; design handlers to be idempotent.
- A lease is a time-bounded claim that lets another worker recover abandoned work.
- Heartbeats distinguish a slow live worker from a crashed one.
- Bounded concurrency protects the database, GitHub API, and any optional AI provider.

## Contract

1. Claim only queued or stale-running jobs whose retry policy allows another attempt.
2. Use database row locks or an equivalent atomic claim so concurrent workers cannot process the same lease at the same time.
3. Record lease owner, lease expiration, attempt count, heartbeat timestamp, started timestamp, and last error category.
4. Heartbeat running jobs at a bounded interval shorter than the lease timeout.
5. Complete jobs only after the analysis result is persisted and associated with the exact repository/PR/head SHA/analysis version.
6. Mark terminal failures separately from retryable failures. Preserve partial analysis results when the pipeline can safely produce them.
7. Recover stale leases after process crash or missed heartbeat; do not require manual cleanup for normal failure cases.
8. Bound worker concurrency with an explicit setting. Do not spawn unbounded tasks per delivery.
9. On shutdown, stop claiming new jobs, let in-flight jobs finish up to a timeout, heartbeat or release safely, then exit with an appropriate status.
10. Do not claim exactly-once processing. Rely on job uniqueness and idempotent writes to make repeated attempts safe.

## TDD loop

Start with a failing lease test:

```bash
uv run pytest tests/unit/test_worker_leases.py::test_two_workers_do_not_claim_same_queued_job -q
```

Expected first failure: worker lease operations do not exist.

Add tests in this order:

- one worker claims one queued job;
- a second worker cannot claim the same active lease;
- stale lease can be reclaimed after timeout;
- heartbeat extends lease and prevents stale reclaim;
- retryable failure returns job to queued with incremented attempt count;
- terminal failure records failed status and error category;
- graceful shutdown stops new claims and handles in-flight work;
- crash simulation proves stale lease recovery creates a later successful attempt.

## Acceptance criteria

- Focused tests prove atomic claim behavior under concurrent workers.
- Stale lease recovery is tested with real persisted state, not only mocked clocks.
- Heartbeat, retry, terminal failure, completed, partial, and failed statuses match the CG-015 job state model.
- Worker concurrency is configurable and bounded.
- A crash between claim and completion does not permanently strand work.
- Repeated processing attempts do not create duplicate final reports for the same repository/PR/head SHA/analysis version.

## Error, security, and recovery cases

- Separate provider rate limit, unauthorized repository, invalid input, transient network failure, and internal bug categories.
- Do not log raw pull-request content, tokens, prompts, model responses containing source, or webhook payloads.
- Do not delete failed jobs automatically; preserve enough evidence for operations and evaluation.
- Prefer monotonic/application time consistently for lease comparisons, and isolate clock-skew assumptions in tests.
