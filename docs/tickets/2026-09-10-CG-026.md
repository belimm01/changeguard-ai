# CG-026 — Publish advisory GitHub Checks through an idempotent outbox

Date: 2026-09-10
Status: Planned
Dependencies: CG-023, CG-025

## Outcome

Completed analysis jobs create advisory GitHub Check Runs through a persisted outbox, with head-SHA safety, external idempotency, readback verification, and clear failure states when publishing is unavailable.

## Design principles

- Publishing to GitHub is an external side effect; persist intent before attempting it.
- At-least-once outbox delivery requires idempotency keys and reconciliation, not hope.
- A Check conclusion is product language: advisory findings are not a merge guarantee.
- Head SHA must match the analyzed commit so stale results do not decorate a newer PR state.

## Contract

1. Commit the analysis report and its publishing outbox intent in one database
   transaction, before any GitHub API call. A crash must not leave a completed
   report without recoverable publishing intent.
2. Include an explicit external id derived from analysis version, repository id, pull request number, head SHA, and report id.
3. Before publishing, verify the current PR head SHA still matches the analyzed head SHA. If stale, mark the outbox item stale and do not publish as current.
4. Publish an advisory Check Run. Use `neutral` for completed advisory reports unless a different conclusion is explicitly justified and tested. Do not use `success` as a guarantee that the PR is safe to merge.
5. If analysis failed or is unavailable, publish or update a distinct Check state/message that says analysis is unavailable; do not fabricate an empty green result.
6. On ambiguous POST failure/timeouts, list Check Runs and reconcile by `external_id` before attempting another create.
7. After create/update, read back the Check Run and persist GitHub id, status, conclusion, head SHA, external id, and URL.
8. Serialize publishing attempts per logical report with durable claims and
   fencing. `external_id` is a reconciliation key, not a GitHub-enforced unique
   constraint. After an ambiguous POST, retain an explicit uncertain state and
   reconcile bounded, paginated reads before any further create. If absence
   cannot be established safely, escalate instead of blindly repeating POST.
9. Logs and Check summaries must not include raw source content, tokens, prompts, or hidden chain-of-thought. Include bounded file paths and finding summaries only.
10. No live GitHub write is allowed while implementing tests unless the user explicitly authorizes a sandbox run.

## TDD loop

Start with a failing payload test:

```bash
uv run pytest tests/unit/test_check_payloads.py::test_completed_advisory_report_uses_neutral_not_success -q
```

Expected first failure: check payload builder does not exist.

Then add tests:

- findings create a bounded advisory summary;
- no findings still uses advisory wording and does not promise merge safety;
- failed analysis creates analysis-unavailable wording;
- stale current head prevents publish;
- outbox retry after timeout lists by external id before create;
- duplicate delivery/retry updates existing Check Run rather than creating another;
- readback mismatch marks publish failed with an explicit reason.
- a crash between report write and transaction commit leaves neither record
  committed; a crash after commit leaves both report and outbox recoverable;
- the head changes between preflight and POST: payload `head_sha` remains the
  analyzed revision, never the newly fetched head. Readback records stale
  status if needed; no check is reassigned to a newer commit;
- ambiguous POST plus temporarily absent list results and an expired lease do
  not cause an immediate duplicate create by a second worker.

## Acceptance criteria

- Outbox records are persisted and retried by the worker with at-least-once semantics.
- Ambiguous GitHub write failures are reconciled by listing existing Checks by `external_id` before repeat creation.
- The published Check is bound to the analyzed head SHA and will not mark stale results as current.
- Readback verification persists the exact Check Run identity and visible URL before success is claimed.
- Advisory language is tested: `neutral` is not treated as a merge guarantee, and unavailable analysis is distinct from clean analysis.
- No test performs live GitHub writes by default.

## Error, security, and concurrency cases

- Handle 401/403 auth failures, 404 repository/check not found, rate limits, validation errors, and network timeouts as distinct outbox failure categories.
- Ensure concurrent workers processing the same outbox item do not create duplicate Check Runs.
- Redact authorization headers and avoid including raw patches in Check output or logs.
- Keep retry limits and backoff bounded and observable.

## Definition of done

- Completed jobs can enqueue and publish advisory Checks through a durable outbox.
- Duplicate retries and ambiguous POST results are safe through external-id reconciliation.
- Publishing success is claimed only after reading back the external Check Run.
- Stale-head and analysis-unavailable paths are visible and tested.
