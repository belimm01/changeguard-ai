# CG-023 — Authenticate GitHub App access and authorize repositories

Date: 2026-09-10
Status: Planned
Dependencies: CG-009, CG-014

## Outcome

ChangeGuard can exchange a GitHub App private key for installation access tokens and authorize every API request against an explicitly allowed installation/repository pair before reading pull-request metadata or file content.

## Design principles

- GitHub App JWTs authenticate the app; installation tokens authorize repository access.
- Least privilege is enforced twice: requested GitHub permissions and local repository/installation authorization.
- Token refresh and revocation are normal races, not exceptional production mysteries.
- Secrets belong at process boundaries and logs must prove behavior without revealing material.

- `src/changeguard/github/auth.py` — JWT creation, installation-token acquisition, refresh policy, and permission checks.
- `src/changeguard/github/authorization.py` — installation/repository authorization decisions.

## Contract

Implement GitHub App authentication without requiring a real GitHub App installation in this ticket.

1. Load these settings from explicit environment variables or the existing configuration system: app id, private-key PEM path or value, webhook secret name/reference if already introduced, token refresh skew, and authorized installation/repository allow-list.
2. Never log the private key, JWT, installation token, webhook secret, authorization header, or full environment dump.
3. Generate JWTs with bounded lifetime and issued-at skew that GitHub accepts; do not cache app JWTs beyond their validity window.
4. Request installation tokens only for the requested installation id and verify the returned repository/permission scope is compatible with the operation.
5. Required GitHub permissions for v1 are: checks write, contents read, pull requests read, and metadata read. Do not request administration, workflows, issues write, or contents write.
6. Before any repository-scoped read or check write, validate that the webhook/API request installation id, repository id/name, and configured allow-list agree.
7. Treat token refresh, revoked installation, suspended installation, 401, 403, and 404 as distinct observable failure categories.
8. Concurrent callers for the same installation should not stampede the token endpoint. Serialize refresh per installation or prove bounded duplicate refreshes.
9. This ticket must not create a real GitHub App, install it into any repository, call live GitHub with real credentials, or write repository checks.

## TDD loop

Start with a failing unit test such as:

```bash
uv run pytest tests/unit/test_github_authorization.py::test_rejects_repository_not_bound_to_installation -q
```

Expected first failure: the authorization module or function does not exist.

Then add tests one behavior at a time:

- valid installation/repository is allowed;
- mismatched repository id/name is denied;
- unknown installation is denied;
- missing or overbroad permission set is denied;
- private key and tokens are redacted in validation/log error strings;
- expired token refreshes before use;
- concurrent refresh for one installation is bounded;
- revoked/suspended installation responses become explicit application errors.

Use mocked `httpx` transports for HTTP behavior. Do not use live credentials.

## Acceptance criteria

- Tests prove authorization denies unknown installations, wrong repositories, missing permissions, suspended/revoked installations, and stale tokens.
- Tests prove no secret values appear in exception messages or structured log fields produced by this layer.
- Installation-token acquisition uses `httpx` through the bounded client pattern from CG-009.
- Token cache behavior is safe under refresh/revoke races and does not rely on exactly-once execution.
- Configuration validation fails closed when GitHub App settings are incomplete in a mode that requires GitHub access.
- Documentation lists the exact proposed GitHub App permissions and states that no real installation is authorized by this ticket.

## Security and error cases

- Fail closed on missing allow-list entries.
- Distinguish authentication failure from repository-not-authorized so operators can fix configuration without exposing secrets.
- Do not accept repository identity solely from a user-supplied URL or branch name.
- Do not downgrade checks write failure into a successful analysis result.
