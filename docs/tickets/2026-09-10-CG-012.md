# CG-012 — Add a scoped Avro compatibility rule

Date: 2026-09-10
Status: Planned
Depends on: CG-010

## Outcome

ChangeGuard compares base/head Avro schemas for a narrow, deterministic compatibility subset and reports breaking schema changes with evidence and explicit unsupported coverage.

## Design principles

- Avro compatibility depends on reader/writer schema evolution rules, not only field-name diffs.
- Start with records and fields before unions, aliases, logical types, or registry-specific behavior.
- Unsupported schema constructs must be visible coverage, not silent pass results.

## Files

Create proposed:

- `src/changeguard/rules/avro.py` — scoped Avro compatibility rule.
- `src/changeguard/parsing/avro.py` — safe JSON schema parsing helpers if useful.
- `tests/unit/rules/test_avro.py` — rule tests for supported changes and unsupported coverage.
- `tests/fixtures/avro/` — small base/head schemas.

Modify existing:

- `src/changeguard/application/analysis.py` or rule composition point — include this rule when content inputs exist.
- `src/changeguard/domain/content.py` and `src/changeguard/domain/reports.py` — reuse evidence and coverage types.

## Supported v1 subset

For Avro record schemas in JSON, explicitly use BACKWARD compatibility:
the head schema is the reader and the base schema is the writer. This checks
whether new consumers can read previously written data; it does not infer
deployment order or promise forward/full compatibility.

- Removing a writer field is compatible: the new reader ignores that field.
- Adding a reader field without a valid default is incompatible.
- Adding a reader field with a valid default is compatible for this subset.
- Apply the specification's primitive type promotions in the reader/writer
  direction, rather than labeling every type change as breaking. Test at least
  writer `int` to reader `long` as compatible and the reverse as incompatible.
- Treat namespace/name changes as incompatible when record full names differ
  and no supported alias resolves them; aliases remain unsupported in v1.
- Report unions, aliases, recursive records, logical types, maps/arrays, and registry subject compatibility as unsupported unless implemented deliberately.

## Acceptance criteria

- The parser accepts JSON Avro schemas from fetched content and rejects invalid JSON with partial coverage.
- Adding a reader field without a valid default and incompatible primitive
  resolution emit findings with file and optional line evidence.
- Removed writer fields, valid reader defaults and allowed primitive promotions
  do not produce breaking-change findings for BACKWARD compatibility.
- Each finding/report names the checked compatibility direction; forward/full
  compatibility is not implied. Invalid schemas/defaults yield partial coverage,
  not a compatibility verdict.
- Unsupported constructs create coverage entries naming the construct and path; they do not become safe results.
- Oversized files, missing base/head content, binary content, and decode errors remain partial.
- The rule does not contact a schema registry or infer deployment topology.
- Findings are advisory and compatible with the report model from CG-008.

## Non-goals

- No complete Avro compatibility engine.
- No Confluent Schema Registry integration.
- No remote references, generated code execution, or runtime consumer analysis.

2. Write the failing test for the expected finding and evidence.
3. Implement minimal safe JSON parse and field-map comparison.
4. Add failing tests for compatible field removal, both directions of primitive
   promotion, and added fields with valid/invalid defaults.
5. Implement deterministic comparisons and non-finding compatible case.
6. Add failing tests for union/logical type unsupported coverage and invalid JSON partial coverage.
7. Wire the rule into the composition point if available, then run gates.
