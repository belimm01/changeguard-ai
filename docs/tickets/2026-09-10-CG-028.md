# CG-028 — Package reproducible container and local Compose deployment

Date: 2026-09-10
Status: Planned
Dependencies: CG-022, CG-027

## Outcome

ChangeGuard can be built into a pinned, non-root container image and run locally through Docker Compose with Postgres, migrations, health checks, resource limits, backup/restore instructions, and a single-host deployment runbook that requires explicit authorization before any live deployment.

## Design principles

- Reproducible deployment starts with pinned dependencies and explicit runtime settings.
- Containers should run as non-root and expose only the required surface.
- Compose is sufficient for the v1 single-host target; Kubernetes is a future extension, not a requirement.
- Backup/restore and rollback are part of release readiness, not afterthoughts.

## Files

Create or update when implementing:

- `Dockerfile` — reproducible Python runtime image using the project lock file.
- `.dockerignore` — exclude local caches, secrets, VCS noise, and test artifacts.
- `compose.yaml` — API, worker, Postgres, migrations, and optional observability endpoints for local operation.
- `scripts/run-migrations.sh` or existing script path — bounded migration runner if scripts already exist.
- `docs/runbooks/local-compose.md` — local startup, shutdown, migration, backup, restore, rollback, and troubleshooting.
- `tests/integration/test_container_health.py` or equivalent smoke test — probes the built service through Compose where feasible.

Read first; extend rather than overwrite:

- `pyproject.toml` and lock file behavior
- health/readiness from CG-027
- injection/leakage regression constraints from CG-022
- existing CI/workflow files before adding build gates in CG-029

## Contract

1. Build the image from pinned project dependencies. Do not install floating latest packages in the runtime image.
2. Run the application as a non-root user. The container filesystem should be read-only where practical, with explicit writable locations only when needed.
3. Configure API and worker roles explicitly; do not require two unrelated images for v1 unless justified.
4. Compose must include Postgres with persistent volume, health check, bounded resources, and local-only defaults.
5. Migrations must be runnable as an explicit one-shot step or service. Startup must not silently skip required migrations.
6. Health checks must use CG-027 `/live` and `/ready` semantics.
7. Secrets must be supplied through environment files or secret references that are ignored by Git; do not commit real credentials.
8. Backup and restore instructions must include actual `pg_dump`/`pg_restore` or equivalent commands and a verification step.
9. The runbook must include rollback steps for image version and database backup restore.
10. No Kubernetes manifests are required for v1. No live deployment is authorized by this ticket.

## TDD/build loop

Start with a failing container smoke check:

```bash
docker build -t changeguard-ai:cg-028 .
```

Expected first failure before implementation: no Dockerfile or incomplete build context.

Then add checks incrementally:

- image builds from a clean checkout using the lock file;
- container runs as non-root;
- Compose starts Postgres and API locally;
- migration step creates/updates schema;
- `/live` and `/ready` reflect service state;
- worker starts and idles without crashing;
- backup and restore commands are tested on disposable local data;
- resource limits and health checks are visible in Compose config.

## Acceptance criteria

- Docker image builds reproducibly from pinned dependencies and does not require network access at runtime except configured external APIs.
- Runtime user is non-root and tests or inspection commands prove it.
- Compose can run API, worker, migrations, and Postgres on a developer machine with local-only defaults.
- Health/readiness checks work through the container boundary.
- Resource limits, restart policy, ports, volumes, and secret handling are explicit.
- Runbook includes migration, backup, restore, rollback, log inspection, and common failure recovery.
- No real deployment, DNS change, GitHub App installation, or external write is performed without explicit approval.

## Security and recovery cases

- Do not copy `.env`, private keys, GitHub tokens, local databases, or test caches into the image.
- Confirm container logs still obey CG-027 privacy rules.
- Handle migration failure by failing readiness and documenting rollback, not by starting with mismatched schema.
- Backup/restore must verify restored data before claiming success.

## Quality gates

Focused commands proposed for this ticket:

```bash
docker build -t changeguard-ai:cg-028 .
docker compose config
docker compose up --build --wait
uv run pytest tests/integration/test_container_health.py -q
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
uv run mypy src tests
uv lock --check
git diff --check
```

Run these commands during implementation and record the real output. If Docker is unavailable, record that and run all non-Docker gates.

## Definition of done

- A reviewer can build and run the local stack from the runbook.
- Migrations, health, backup, restore, and rollback are demonstrated on disposable local data.
- The v1 deployment target is documented as single-host Compose; Kubernetes remains a non-goal.
