# CG-029 — Add CI security, quality, build, and evaluation gates

Date: 2026-09-10
Status: Planned — baseline CI (lint, format, strict types, tests with PostgreSQL) exists; security, container and evaluation gates pending
Dependencies: CG-021, CG-022, CG-028

## Outcome

The repository has CI gates that run the existing Python quality checks, Postgres-backed tests, container build, security checks, and offline evaluation/leakage regressions using pinned actions and fork-safe secret handling.

## Design principles

- CI should verify the same commands developers run locally, then add environment-specific gates such as containers and security scanning.
- Forked pull requests are untrusted; never expose repository secrets to them.
- Actions and external build steps are supply-chain dependencies and should be pinned deliberately.
- Evaluation gates must be deterministic enough to fail real regressions without creating flaky release theater.

## Files

Create or update when implementing:

- `.github/workflows/ci.yml` or the existing workflow file after inspection — Python quality, tests, Postgres service, security, build, and eval gates.
- `.github/dependabot.yml` or existing dependency-update config, if project policy wants automated action/dependency updates.
- `docs/ci.md` — gate purpose, fork-secret policy, and how to reproduce locally.
- `tests/**` only as needed to make existing gates executable, not to weaken coverage.

Read first; extend rather than overwrite:

- all existing `.github/workflows/*.yml` files
- `pyproject.toml`, lock file, and Python version constraints
- Compose/container artifacts from CG-028
- offline eval from CG-021
- injection/leakage regressions from CG-022

## Contract

1. Inspect existing workflows before editing. Extend them or add a focused new workflow; do not overwrite existing CI by assumption.
2. Use `uv` with frozen/locked dependency installation. CI must fail if the lock file is stale.
3. Run the baseline gates: `pytest`, Ruff check, Ruff format check, strict mypy, lock check, and diff whitespace check where supported.
4. Run Postgres-backed integration tests using a CI service container or Compose pattern from CG-028.
5. Build the Docker image and run at least one container health/readiness smoke check.
6. Run offline evaluation from CG-021 and injection/leakage regression tests from CG-022 with deterministic fixtures and no real AI-provider calls by default.
7. Configure secret-using jobs so they do not run with secrets on untrusted forks. No GitHub App private key, installation token, provider key, or deployment credential should be exposed to PR code.
8. Pin GitHub Actions to full commit SHAs before implementation is accepted, or document a reviewed policy exception with compensating controls.
9. Set explicit job permissions using least privilege, such as read-only contents for most jobs. Do not grant broad write permissions globally.
10. Do not add deployment, live GitHub Check publishing, or external writes to CI in this ticket.

## Small YAML pattern example

Example only — least-privilege job permission shape:

```yaml
permissions:
  contents: read

jobs:
  quality:
    permissions:
      contents: read
```

Grant write permissions only to a job that truly writes, and this ticket should not introduce live write jobs.

## Acceptance criteria

- Existing workflows were inspected and the final diff does not delete unrelated gates.
- CI installs dependencies with `uv` in locked/frozen mode and verifies the lock file.
- CI runs unit tests, integration tests with Postgres, lint, format check, strict typecheck, container build/smoke, offline eval, and injection/leakage regressions.
- Secret handling is fork-safe by construction; tests/jobs that require secrets are skipped or disabled for untrusted PRs rather than failing open.
- Actions are pinned to commit SHAs or an explicit reviewed exception is documented.
- Workflow permissions are least-privilege and no deployment/external write is added.
- Local reproduction commands are documented.

## Security and reliability cases

- Avoid `pull_request_target` for running untrusted code unless there is a very specific, reviewed, non-checkout use case.
- Do not print environment variables or secrets during debugging.
- Make eval thresholds explicit and stable; if a corpus fixture changes, require evidence in the PR.
- Use cache keys that do not restore untrusted executable artifacts into privileged jobs.
